# Проверка исходного JAR 2.0.1

1. **Неверные скобки в формуле HP.** Реально выполняется `H + H * scale * N - 1`, а не `H + H * scale * (N - 1)`. При H=20, scale=1, N=2 получается 59 вместо 40.
2. **FinalizeSpawn не охватывает все способы появления мобов.** Программное создание, в том числе скрипты, может обходить этот вызов. Перенесено на серверный `EntityJoinLevelEvent`; загрузка с диска и повторное масштабирование исключены.
3. **Поиск по кубу и целочисленной позиции.** AABB радиуса 40 включал углы дальше 40 блоков. Теперь точная позиция, квадрат евклидова расстояния <=1600; spectator и мёртвые исключены.
4. **Получатели не фиксировались.** Список строился при обработке каждого предмета на момент смерти. Теперь список UUID фиксируется при спавне и сохраняется с мобом.
5. **Дроп зависел от ServerPlayer в DamageSource.** Убийства окружением или другими источниками обходили персонализацию. Теперь используется Forge LivingDropsEvent независимо от типа убийцы.
6. **Один ItemStack передавался нескольким сущностям.** Изменение одной копии могло затронуть остальные. Теперь у каждой копии самостоятельный ItemStack.copy().
7. **Незарегистрированный IndividualItemEntity.** Подкласс создавался с vanilla EntityType.ITEM; после загрузки создавался обычный ItemEntity без логики подкласса. Используется vanilla ItemEntity с Forge persistent NBT и серверными Mixin.
8. **Повреждение NBT предмета.** setItemOwner вызывал setTag(new CompoundTag()), заменяя исходный NBT целиком. Владение перенесено в NBT сущности, ItemStack не меняется.
9. **Неполная защита от слияния.** Mixin проверял только аргумент tryToMerge, а не текущую сущность. Теперь блокируются оба направления.
10. **Пустая перезагрузка KubeJS.** onServerReload ничего не очищал, удалённые записи могли оставаться. Реестр очищается перед повторным выполнением server scripts; параметры уже появившихся мобов сохранены в NBT.
11. **Хрупкий захват локальных переменных dropFromLootTable.** Удалена инъекция CAPTURE_FAILHARD в пользу Forge event; Mixin используются только на коротких входах методов.
12. **Воронки могли забирать личный дроп.** Стандартный путь HopperBlockEntity.addItem(Container, ItemEntity) блокируется для персональных предметов.

Список items в исходном API фактически означал общий дроп, который не дублируется; этот смысл сохранён. Исходный `solo` создавал обычный предмет без владельца — имя параметра не означало персональную выдачу убийце.

Исправления действуют для новых мобов. Если при первом спавне нет игроков, сохраняется пустой список, здоровье остаётся базовым, дроп обычным. Тот, кто приходит после спавна, не получает копию. Игрок, ушедший после спавна, остаётся владельцем своего выпавшего предмета. Спорные продуктовые решения описаны явно, чтобы можно было изменить их при необходимости.
